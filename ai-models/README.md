# ai-models

The single registry of the **AI models** this project can use: speech recognition, language, speech synthesis, voice activity and turn detection. It is named `ai-models` on purpose, so it is never confused with contracts or data models.

Status: **design, one example manifest.** Nothing reads this folder yet.

## Why it exists

Three things need the same facts about each model, and they should never disagree:

| Reader | Needs |
|---|---|
| **Fit calculator** (SPEC §8.3) | Parameters, architecture (for KV-cache size), file size per quantization, runtimes, license |
| **[testing/](../testing/README.md)** | The list of candidates per slot, to build the contract-test matrix |
| **[benchmarking/](../benchmarking/README.md)** | The list of candidates per slot, to build the experiment matrix |

Adding a model here makes it a candidate everywhere. Removing it removes it everywhere.

## Layout

```
ai-models/
  README.md
  manifests/        one file per model family variant, e.g. qwen3.5-4b.yaml
```

## What a manifest holds

Facts only, each with a source. Weights are never stored in the repo (SPEC §10); setup downloads them.

| Field | Meaning |
|---|---|
| `id`, `family` | Stable slug and the ladder it belongs to |
| `slots` | Which roles it can hold (listening, transcription, interviewer, evaluator, speech) |
| `license` | SPDX identifier, and whether it is ungated and downloadable at setup |
| `license_status` | `clear` or `question`. A model with a question is excluded from SPEC §3.2 until settled |
| `params` | Total and active (for mixture-of-experts) |
| `architecture` | Layers, KV heads, head dimension, which layers carry a context cache, window size. Everything the KV-cache formula needs |
| `variants` | One entry per quantization: file name, size, hash, download URL |
| `runtimes` | Where it runs: CPU, CUDA, Metal, Vulkan, with the runtime and version tested |
| `streaming` | Whether it streams natively |
| `languages` | Supported languages |
| `sources` | URLs and the date each fact was read |

## What a manifest does not hold

- **Measured results** (memory, speed, quality). Those are generated by test and benchmark runs, live in their `results/` folders, and are never written back by hand.
- **Decisions.** Which model is the default for a tier belongs in `SPEC.md` §3.2.1 and `docs/decisions/`, not here.

## Rules

- Every fact cites a source, and unconfirmed facts are marked `unverified: true`, as the SPEC marks them.
- A manifest value must be the exact file the setup will download. A fit calculator that uses a different file size than the real one is wrong.
- Change a manifest only with a source. If a measured result disagrees with a manifest, fix the manifest and record why.
