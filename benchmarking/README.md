# benchmarking

Benchmarking answers: **how well does each model do the job of the role it holds?** A model only enters a benchmark after it passes the contract tests in [`testing/`](../testing/README.md).

Status: **framework design, no code yet.** Every number the SPEC marks **[unverified]** is a benchmark waiting to be written. The first targets are SPEC §12 items 2, 11, 12 and 13.

## Roles and what is measured

Each role has its own suite in `roles/`, with its own dataset and metrics. Every role also records the **resource cost**: peak RAM and VRAM, CPU time, load time, and warm and cold start.

| Role (SPEC §3.2) | Effectiveness metrics | Dataset needs |
|---|---|---|
| **Listening** | False cutoffs, missed turns, end-of-turn delay | Conversational audio with labeled turn ends, including hesitations and trailing pauses |
| **Transcription** | Word error rate on interview-style speech, delay from end of speech to final text, real-time factor | Accented and noisy speech, domain terms (job titles, technologies), with reference transcripts |
| **Follow-up decider** | Agreement with labeled "probe or move on" decisions | Transcript snippets labeled by a human |
| **Interviewer** | Time to first sentence, tokens per second, adherence to constraints (one question, one or two sentences, stays on topic), follow-up relevance | Scripted interview scenarios with resume and job description |
| **Evaluator** | Agreement with human-scored transcripts, score stability across repeated runs, STAR detection accuracy | Human-scored interview transcripts |
| **Speech** | Time to first audio, real-time factor, intelligibility (round-trip word error rate through a fixed STT), naturalness proxy | Interviewer-style sentences |
| **End to end** | Turn-end to first-audio delay at p50, p95 and p99 with every slot running together; memory and CPU under contention | Full scripted sessions |

Effectiveness is never reported without the cost beside it. A better model that does not fit the tier is not a win for that tier.

## Experiments

An experiment is the unit of model experimentation. It is a file in `experiments/` that declares:

- the **candidate** for each slot (any registered model, quantization and runtime), so changing one slot at a time or several together is a config change, not a code change;
- the **hardware profile** (SPEC §8.2 tier, plus optional core pinning and RAM limit from §8.6), so a developer machine can imitate a minimum-spec machine;
- the **datasets** and **repeat count**;
- the **seed**.

Example (shape only):

```yaml
name: tier1-llm-compare
profile: { tier: 1, cores: 4, ram_limit_gb: 6 }
slots:
  interviewer:
    - { model: qwen3.5-4b, quant: Q4_K_M }
    - { model: qwen3.5-2b, quant: Q8_0 }
  speech: { model: kokoro }
datasets: [interview-scenarios-v1]
repeats: 5
seed: 1234
```

The runner expands this into a matrix, runs each cell, and stores one row per run.

## Consistency and comparability

- **Report the spread, not only the mean.** p50, p95 and p99, over repeated runs, because SPEC §3.2.2 chooses defaults for *consistent* latency.
- **Record the environment** with every run: CPU, RAM, GPU and driver, OS, runtime and model versions, thread pinning, free memory at start, and the dataset hash.
- **Runs are comparable only when** the model files, dataset hashes and runtime versions match. Otherwise the scoreboard marks the comparison as invalid.
- Hardware disclaimer: results are tied to the machine that produced them. A scoreboard row always names its hardware, and a number from the dev machine is never presented as a minimum-spec result.

## Results

Runs write files to `benchmarking/results/` (gitignored). One script loads them into a SQLite database and generates scoreboards. The script is role-agnostic, and each role supplies its own schema and scoreboard queries, because only the role knows what it measures. Results and databases are generated, never committed and never edited by hand. Generated scoreboards carry a "Generated by" line.

## Datasets

The benchmark dataset is a set of full-length mock interviews, about two hours in total, written and recorded by Steven playing both the interviewer and the interviewee. Because the speaker is also the author, consent and licensing are simple. The recordings need the following before they can score anything:

- a reference transcript for each recording, for word error rate;
- labeled turn boundaries (where each speaker really finished), for the listening role;
- "probe or move on" labels at each interviewer decision point, for the follow-up decider;
- scored answers, for the evaluator.

Limits to state with every result: a single speaker voices both roles, so accent, microphone and speaking style are narrow. Scores from this set describe that speaker and should not be presented as general accuracy. Adding other speakers later widens the set.

Until the recordings exist, benchmarking waits. The early passes are testing only (see `testing/README.md`).

3. Naturalness metric for speech. A learned predictor such as UTMOS has been used in published benchmarks; confirm it suits our voices.
4. The candidate list lives in [`ai-models/`](../ai-models/README.md), shared with `testing/` and the fit calculator.
5. Run types, for example exploratory runs versus runs that are committed as the official comparison.
6. First targets: 4-core x86 measurements of the combined stack, time to first token on 2-4K prompts, the Gemma 4 KV-cache size, and p50 versus p95 turn latency with TTS on CPU versus GPU.
